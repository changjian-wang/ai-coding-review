## 1. 产品决策摘要

下一阶段聚焦 **Review 判断质量**，而不是扩展通用 Agent、协作平台或工作台功能数量。

> 以已确认需求为审查基准，在真实业务链路中验证实现；同时通过实现逻辑、系统事实和反例验证需求本身。精准识别真正需要修复的问题，也能识别看似有瑕疵、实际符合业务约束的合理实现。

核心闭环：

**确认需求与假设 → 建立业务影响链 → 检查实现与需求 → 独立发现系统性问题 → 验证与反证 → 输出有依据的审查结论。**

本轮不把以下内容当作差异化目标：

- 评论更多、扫描行数更多或调用更多模型。
- 只检查命名、格式、防御性写法或孤立的最佳实践。
- 通过只报显而易见的问题来制造高准确率。
- 把同一份不充分上下文反复交给模型，称为独立验证。
- 把代码现状反推成需求，再证明代码符合这份“需求”。
- 把编辑器展示过、模型收到过、问题已处置等同于代码被理解或业务正确。

## 2. 已确认的产品基线

以下五项已经过本次交互确认，不作为待决定选项：

| 决策 | 已确认行为 | 产品影响 |
|---|---|---|
| D-01 需求基线 | 支持粘贴文本、授权需求链接、本地文件读取；AI 整理理解与检查清单后由人确认，PR 资料按需补充 | 原文要求、人工补充、推导检查点和待核实前提分别展示；确认理解不等于需求正确 |
| D-02 缺少需求 | 允许继续技术/逻辑审查，但明确需求未验证，不声称全面满足需求 | 不因缺少需求而禁止所有使用，也不能输出虚假的需求通过结论 |
| D-03 问题范围 | 先选 Repository，再选 PR 或分支；分支默认比较变更并明确基线，可明确选择全量快照；整文件及相关业务链审查，既有问题也报告并区分归因 | 文件来自确定的代码范围而非猜测业务入口；PR/Diff 不将审查限定为新增行 |
| D-04 执行方式 | 一键发起范围审查，按相关业务链组织分析，保留逐文件查看与重审 | 用户不必逐个文件点击才能完成一次正式审查 |
| D-05 结论约束 | 未解决的关键需求矛盾或必要前提禁止直接通过，允许提交评论或要求修改；非关键未知只展示 | 区分“可以提交反馈”和“可以批准”，不继续共用一个笼统的就绪布尔值 |

默认延续现有 VS Code、Copilot 模型和 GitHub 使用方式，不在本阶段建设新的服务端、账号体系或其他代码托管平台适配。

## 3. 产品目标与不做事项

### 3.1 目标

- **精准：** 对每个确认问题说明真实触发条件、行为路径、影响及证据，降低由上下文缺失造成的误报。
- **有全局观：** 发现文件单看合理、组合后破坏业务契约的问题，而不只是复核局部发现。
- **不脱离需求：** 检查实现是否满足已确认的目标、规则和验收条件，识别遗漏与擅自扩展。
- **不盲信需求：** 识别需求内部矛盾、错误假设、无法闭合的状态及与系统事实的冲突。
- **不过度推断：** 合理取舍、证据不足、可选改进与确认缺陷分开，不能混成同一个问题列表。
- **结论有边界：** 说明审查依据、范围、未知项和未完成部分，不将无发现等同于无缺陷。

### 3.2 非目标

- 重建 IDE、通用编程 Agent 或企业研发协作平台。
- 本阶段接入 Slack、Jira、Confluence 等全量企业知识系统，或建设跨仓库知识图谱服务。
- 默认自动修复、自动提交代码、自动批准 PR 或自动合并。
- 默认执行任意仓库脚本或自动调用生产系统验证。
- 将风格和重构建议作为正式 Review 的主要输出。
- 以本地插件门禁声称能够阻止 GitHub 页面上的合并。
- 保证找到所有缺陷、保证模型逐行理解或承诺零误报。

现有修复方案、应用/撤销、评论、翻译和讲解等能力继续保留，但本轮不以扩展这些功能为目标。

## 5. 用户与核心使用场景

主要服务已有本地代码和模型授权的开发者、维护者与 reviewer，尤其关注多文件、跨层、包含业务约束的变更。

| 场景 | 用户需要解决的问题 | 期望结果 |
|---|---|---|
| 审查 AI 或人工生成的变更 | 代码看起来可运行，但不知道需求是否真正落地 | 指出具体遗漏、偏离或错误，而非罗列泛化建议 |
| 审查已有模块 | 没有清晰的新需求或 Diff，也想发现实际逻辑问题 | 允许有边界的技术审查，既有问题来源清楚 |
| 排除局部误报 | 某文件缺少校验/重试，但可能由其他层负责 | 查明实际保障及适用路径，成立则不误报 |
| 检查系统性问题 | 接口、配置、状态机或异步链路组合后出现缺陷 | 按同一失败机制报告，而不是拆成多个文件建议 |
| 验证需求本身 | 忠实实现字面需求，却可能导致业务损失 | 识别需求的错误前提或矛盾，交由人确认，不擅自改写 |
| 给出结论 | 有关键未知、局部失败或需求冲突时不知能否通过 | 可提交有边界的评论/要求修改，但不能伪装完整通过 |

## 6. 关键概念与判断边界

### 6.1 需求依据不是一个不可质疑的优先级列表

不同材料承担不同职责：

| 材料角色 | 作用 | 不能据此推出 |
|---|---|---|
| 已确认需求、目标和验收条件 | 规范本次应该实现什么 | 需求的假设一定真实、各条要求一定兼容 |
| 当前实现、实际配置、契约和可重复观测 | 证明系统现在如何工作及受到什么限制 | 当前做法就是正确需求，或历史缺陷应当继续保留 |
| 设计文档、历史 PR 和明确的取舍记录 | 解释为何这样设计、哪些例外曾被接受 | 旧决策仍适用，或团队曾忽略的问题就不是缺陷 |
| 测试 | 证明特定输入和场景的实际/预期行为 | 需求正确、全部路径安全、未覆盖情况不会发生 |
| 模型推断 | 形成候选假设和待核实问题 | 已获得授权的新需求或确定的业务事实 |

来源冲突必须显式呈现，不能静默选择更容易支持模型结论的一方。新需求可以有意改变旧行为，但必须识别变更意图、迁移条件及影响，不能把“不同于旧实现”本身判为错误。

### 6.2 审查对象

- **实现缺陷：** 已确认目标或必要契约合理，但代码没有正确实现。
- **需求缺陷：** 即使忠实实现字面要求，仍因矛盾、错误假设或不成立的边界而破坏业务目标。
- **证据不足的待核实项：** 尚不能判断需求或实现是否有问题，不冒充 conditional bug。
- **合理取舍：** 有证据证明当前实现符合适用约束，不输出为缺陷。
- **可选改进：** 不改变正确性结论，默认不混入正式缺陷列表。

“特定条件下发生的确认缺陷”与“条件是否存在尚未核实”必须分开：前者可有充分证据，后者仍是未知。

### 6.3 关键未决项

仅当某个尚未解决的问题会改变核心业务结果、决定需求能否成立，或决定严重缺陷是否成立时，才作为关键未决项阻止批准。

标为关键必须说明：

1. 哪个具体结论依赖该前提。
2. 可能造成什么业务后果。
3. 缺少或冲突的证据是什么。
4. 需要谁确认什么，或需要补充哪种验证。

不能因为“模型不确定”“存在任意未知”就全部升级为关键；不能因为需要批准就随意降为非关键。用户可纠正分类，但必须记录理由和依据。

## 7. P0 功能需求

以下全部属于本阶段正式闭环；后文 P1 不作为首版依赖。

### FR-01 需求基线建立与确认

- 允许粘贴需求/设计内容、提供授权需求链接、选择本地文件读取，可组合添加本次目标、业务约束、例外与明确的不做事项；保留原文快照与读取状态。
- 按需纳入当前 PR 的描述和用户明确指定的关联材料；只读取有权限且被授权纳入的来源，不要求接入新平台。
- 按条目或片段区分“应该做到什么”的规范性要求与“实际如何运行”的事实背景，不要求用户给整份材料二选一分类。PR Description 可同时包含改动摘要和验收说明，前者不能反推为需求，明确的验收片段可以作为待确认要求。
- AI 整理为可引用的条目：目标、业务规则、验收条件、前提假设、适用范围与例外。
- “AI 对本次需求的理解”区分原文明确要求、人工补充/修订、推导检查点与待核实前提。能判定时形成验收条件；条件不足时指出缺口，不把“响应及时”擅自量化为未被授权的硬阈值。
- 推导检查点服务于验证已有要求，不自动增加验收门槛；新增规范需由人明确补充/确认并标注来源。可以读取必要仓库上下文消歧，但不从现有实现反推已确认需求。
- 来源选定或变化后自动更新审查理解，不把“手动整理候选”作为前置动作。明确的结构化人工需求可直接纳入理解；只需一次“确认需求并开始审查”，不叠加逐条勾选、整体勾选和单独确认按钮。自动整理不得替代这次明确确认。
- 每条保留来源位置及原文片段，区分原文、模型提取和模型推断；不得改写原文来消除矛盾。
- 原文快照与人工修订的条目分别保存；来源更新或移出后标记引用过期。多来源相互冲突时保留双方与待澄清项，不自动按材料类型、时间或数量决定谁正确。
- 人工可修订、排除或确认；经确认的条目形成版本化基线。推断只有经明确确认才能成为规范性依据，且其事实前提仍可被验证。
- 最后确认表示理解准确且适用于本次代码范围，不保证需求正确、完整或前提成立；未知允许进入审查核实，仍按关键影响决定是否禁止批准。
- 已确认基线可复用；材料或补充说明变化时展示差异，只要求重新确认受影响内容。
- Repository、PR/分支或范围变化后，旧范围的不适用不能静默沿用。保留原文、理由和旧范围记录，重新纳入本次理解待核对；仍不适用时可重新说明原因，不额外增加必经确认步骤。
- 材料过长、格式不支持、解析失败或读取受限时显式报告，不能默认为已完整读取。
- 确认前不启动宣称具备需求一致性结论的正式审查。未提供明确要求时可直接开始，自动标明“需求一致性未评审”，不要求另选审查方式，也不能忽略已知关键问题。

### FR-02 缺需求与局部需求的有边界审查

- 支持“需求驱动审查”和“有限技术审查”两种明确状态，不因缺需求而让产品不可用。
- 两种状态由本次是否有明确且已确认的要求决定，不是用户必须配置的模式选择，也不代表技术审查可以缺少全局观。
- 有限技术审查继续检查可证实的逻辑、契约、兼容性、数据和异常行为，不从代码自动生成已确认需求。
- 部分需求已知时按条目标记评审范围；未知部分不得自动补为“满足”。
- 用户可以在审查中补充需求，经确认后只重审受影响判断。
- 报告及 PR/本地结论保留“需求一致性未评审/部分评审”的说明，不只在入口弹一次提示。
- 有限技术审查允许人工批准其明确的技术范围，但不得表述为需求全部满足。
- 切换到技术审查不能抹除已知且仍相关的关键需求矛盾。

### FR-03 业务影响链与审查单元

- 先确定 Repository 与 PR/分支。PR 使用对应变更列表和代码版本；分支变更必须显示比较基线，全量审查使用所选分支快照而不依赖 Diff 定义范围。
- 起始审查文件来自明确选择的范围，不能把纳入文件统一称为“业务入口”。真正的路由、消息或任务入口只能在取得注册/调用证据后说明。
- 以选定范围为入口，结合需求条目识别相关的入口、调用、状态、数据、接口、配置和异步/并发边界。
- 围绕同一业务行为组织相关文件，而不是只按目录相邻或文件数量分组。
- 复用现有定义/引用和仓库检索；纯代码调用关系不足时，允许读取相关 schema、配置、事件处理、测试和设计依据。
- 每个审查单元说明业务目标、涉及范围、关键契约、已知保障与未知边界，并能追溯到来源。
- 不要求用户手工画图，也不要求先搭建图数据库或为整个仓库建立完美模型。
- 不机械扫描所有文件；按具体判断需要扩展证据。在预算不足时说明哪条判断受限，不能虚构完整的业务链。
- 对动态调用、外部服务或未连接仓库，不推断其隐藏实现；必要时形成明确的契约问题。
- 分组之后仍需检查组间共享状态和契约；不能把互相关联的业务拆开后失去全局视角。

### FR-04 实现对需求的逐项校验

- 对每个范围内的已确认需求，检查实现覆盖、正常/异常路径、验收条件、兼容性和明确例外。
- 输出状态至少区分：有证据支持、被证据违反、证据不足、不适用。
- “有证据支持”必须说明验证到的具体范围，不是宣称所有可能执行均正确。
- 检查遗漏实现、只完成正常路径、半落地契约、跨入口行为不一致和未获确认的行为扩展。
- 对需求含糊、尚未确认或明确不在范围的能力，不以“缺少最佳实践”为由新增产品要求。
- 没有 finding 不自动意味着所有需求满足；每条需求都应有单独的状态和依据。

### FR-05 用实现逻辑反向验证需求

- 检查同一需求内部，以及多条需求组合后的逻辑一致性。
- 对关键假设，利用系统契约、状态转换、异常路径和可重复观测验证其是否成立。
- 对“严格照做仍会失败”的情况，指出错误前提、最小反例、影响及与目标的矛盾。
- 将需求缺陷与实现缺陷分开，允许问题定位到需求条目/文档，不强行伪造源码行号。
- 可以提出待确认的修正方向，但不能自行替换已确认需求、改写验收标准或默认实施新方案。
- 若要求有意改变旧契约，应验证迁移和兼容方案，而不是仅因旧实现不同就否定新需求。
- 若只是产品取舍不同但没有逻辑冲突或实际失败证据，不升级成需求缺陷。
- 关键矛盾进入澄清流程；没有依据时不得用“按需求实现”终止分析，也不得用“需求可能错了”逃避实现检查。

### FR-06 独立发现跨文件和系统性缺陷

- 除局部候选复核外，必须有业务链级的独立发现过程，不只给已有 finding 做总结。
- 重点关注需求遗漏、生产者/消费者契约、状态闭合、幂等/重试、事务与异步边界、缓存失效、权限传递和配置兼容等实际行为。
- 从实际可达的路径说明失败机制；不输出与当前范围无关的全仓库顺手审查。
- 保留整文件逻辑审查；Diff 用于辨别旧行为、新行为和问题来源，不是唯一可报告位置。
- 区分本次引入、既有问题、本次暴露和无法确定；无法确定时不编造归因。
- 同一根因跨文件表现合并为一个问题，保留关联位置；不同触发条件或不同修复责任不强行合并。
- 相关文件不在原范围时，区分“读取为证据”和“新增正式审查对象”。按现有方式加入相关问题文件时须标明理由与新增范围。
- 范围详情分为本次审查、按判断需要的关联核查及实际覆盖限制；显示纳入/关联原因与核查状态。准备时关联范围尚未分析就明确待确定，读取不等于已验证或完成整文件审查。

### FR-07 候选问题的验证与反证

- 候选不是正式确认问题，必须先核实触发条件、调用路径、被破坏的契约与实际影响。
- 主动查找可能推翻候选的证据：上游保证、其他层职责、有效配置、边界限制、已确认例外、适用测试和历史决策。
- 发现与复核应读取同一版本的相关需求和证据；复核不得仅看到候选文本和几行 Diff 就作全局裁决。
- 若缺少决定性证据，允许明确请求补充和再次检索；仍无法得到时标为待核实，不能强行 confirmed 或 dismissed。
- 核查保护是否覆盖相关可达路径；“某一入口已有校验”不能证明所有入口安全。
- 历史偏好、一次忽略、测试通过或模型间意见一致，不单独构成正确性证明。
- 被推翻的候选不继续混入正式缺陷和修复入口；保留可查看的推翻原因。
- 局部判断可以被全局证据推翻；更新必须同步影响问题列表、处置与结论，不保留过时的阻断或通过。
- 语义上的独立验证是职责分离，不强制多模型或固定 Agent 数量；具体调用组织以效果与成本验证决定。

### FR-08 结果分类、严重度与定位

- 正式结果区分需求缺陷、实现缺陷和待核实项；合理取舍与可选改进不计入已确认缺陷。
- 严重度依据实际业务影响，判断确定性依据证据，两者与问题类型分别表达，不继续混用一个字段承担全部含义。
- 已确认问题需包含：一句话结论、需求/契约依据、触发条件、关键行为路径、实际影响、来源位置、支持证据与反证检查结果。
- 没有显式需求依据的技术缺陷，说明被破坏的可证实技术契约；不得伪造需求编号。
- 需求问题锚定原文和条目；代码问题锚定真实源码内容；跨文件问题同时展示关键关联位置。
- 单纯文本推演、已执行复现、已有测试结果和未执行验证明确区分，不虚称“已复现”。
- 对本次修复的方向只给满足已确认需求的最小必要建议，不把修复变成需求扩展或无关重构。
- 复用现有修复/撤销能力时，只允许对具有有效代码位置和可执行修改方向的问题启用；需求矛盾尚未确认解决前，不将建议直接变成改代码操作。
- 不支持将文档位置发布为伪造的 PR 代码行评论；使用审查摘要或一般评论，并保留需求引用。

### FR-09 一键编排、范围状态与异常

- 用户确定范围、按需提供材料后，可一次确认本次理解并启动完整流程；没有明确需求或基线未变化时直接开始。逐文件查看与重审仍保留。
- 展示需求准备、影响链建立、分析、复核、汇总等真实状态，不用虚构进度或 ETA 证明完成。
- 每个范围项最终有完成、明确排除、失败、取消、预算受限或待重审状态；已发送上下文不是完成证明。
- 配置、schema、测试、删除和重命名不能一概作为噪声跳过；相关删除需利用旧侧证据判断契约影响。
- 分析预算按业务判断需要使用；达到边界时显式解释受影响单元及恢复方式。
- 用户取消后停止后续调用，不混入迟到结果；已完成且仍有效的结果可以保留。
- 模型错误、无效结构化输出、读取失败、超时和部分任务失败不得转换为空发现或成功。
- 支持针对失败/受限/变更单元继续或重试，不要求无差别重跑全部。
- 正式完整批准需要对应审查流程完成；评论/要求修改可以提交有效的部分结果，但必须带未完成范围说明。

### FR-10 快照、依赖与结果失效

- 审查结果绑定源码内容、范围、已确认需求版本和审查规则版本；能取得时记录模型标识。
- 需求原文、用户补充、实现、关键调用方、配置或契约变化时，相关结论应失效并待重审。
- 源文件未修改但其依赖保障被移除时，也不能复用旧的误报豁免或通过结论。
- 无法可靠确定影响范围时，扩大重审范围并解释原因，不猜测安全复用。
- 同一问题在重审后保持处置关联需有可靠匹配；位置/标题相似但语义不同不能误继承。
- 旧进度可保留为历史，但旧“已分析”“全局已确认”不能替代新的需求感知审查完成状态。
- 异步返回与当前快照不一致时，标为过期，不覆盖较新的有效结果。

### FR-11 关键澄清与分结论门禁

- 在工作台列出关键未决项，给出问题、依据、影响、可回答的具体问题及解除条件。
- 允许用户补材料、回答问题或修订需求；新确认版本触发相关重审。
- 将“已评论”“已阅读”“已忽略”与“矛盾已解决/前提已证实”分开。动作完成不能静默解除关键阻断。
- 允许通过证据证明不适用，或明确修订本次目标/范围解除相关性；必须留有记录，不能作为一键绕过已知关键问题的捷径。
- 非关键未知只展示，不升级为所有未决项一律阻断。
- 需求问题的处置还需支持待确认、需求已修订、证据已补充、确认不适用等含义，不能机械套用“代码已修复”。
- 门禁仅约束产品内的提交入口，不声称执行 GitHub 分支保护。

结论规则：

| 结论 | 允许条件 | 输出要求 |
|---|---|---|
| 通过 | 当前范围的必要审查完成、结果未失效、人工确认成立、可操作问题按规则处置，且没有仍相关的关键需求矛盾/必要前提未决 | 写清需求覆盖与技术范围；有限技术审查不能声称需求通过 |
| 要求修改 | 已有有效、可提交的问题证据；允许关键项未解决或流程部分未完成 | 指出需要修改/确认的内容及未完成范围 |
| 仅评论 | 有有效反馈可提交；允许关键项未解决或流程部分未完成 | 不将意见提交成功说成审查通过或问题已解决 |

用户最终决定提交何种有效结论；系统不自动批准。现有 finding 处置机制与新增需求澄清状态需要协同，不能只在 UI 禁用按钮而底层提交仍可绕过规则。

### FR-12 反馈与可修订的业务例外

- 用户指出误报时，允许补充原因、适用范围和证据，触发相关判断重新验证。
- 区分“不是缺陷”“确认缺陷但暂缓处理”“业务接受的取舍”“资料不足”，不能把所有忽略当作训练反例。
- 将本次补充保留在对应审查上下文；要沉淀为以后使用的例外，需明确确认其适用条件。
- 例外可查看、修订和删除；依赖条件失效时重新评估。
- 未获确认的单次反馈不能成为全仓库的永久免责规则。
- 本阶段不建设全量历史 PR 挖掘或自动学习平台；优先利用当前会话与用户明确指定的历史材料。

### FR-13 验证方式与能力边界

- 逻辑验证可采用契约核对、状态推演、反例及现有测试证据，不强制每个问题都运行程序。
- 需要执行测试/复现时说明目的、范围与前置条件；沿用用户授权流程，不默认执行不可信脚本、访问生产数据或启用网络。
- 模型未实际执行工具，或只生成了一段测试，不能标为“执行验证通过”。
- 不要求本阶段交付通用自动测试平台或修复验证 Agent。
- Token/预算延续估算口径；无法取得供应方账单时不显示伪精确费用。
- 新增 UI 与模型输出遵循现有语言配置和中英双语，不破坏切换、恢复及已有审查操作。
- 新增需求材料的读取、进入模型上下文和持久化范围需明确；不因一键审查自动上传无关文档或引入新的第三方数据接收方。
- 仓库内容、需求附件和 PR 正文是待解释的数据，不能用来改变工具权限、伪造用户确认或取消审查规则。

## 8. 最小交互闭环

以最佳审查任务重新设计工作台，不将旧布局或早期原型作为兼容约束；选择性复用范围、Diff、定位、模型接入等可靠基础能力。三个阶段为准备、审查、结论，核心审查阶段以源码为主场：

1. **准备：** 简洁单列三块：选择审查对象（Repository、PR/分支及必要基线）、提供需求依据（粘贴/链接/本地文件）、AI 对本次需求的理解。不逐份分类，不添加额外流程配置或勾选。
2. **确认并开始：** 展示检查清单/验收条件，区分原文要求、人工补充、推导检查点、待核实前提；出处、版本、修订和有理由排除放在详情中。一次“确认需求并开始审查”建立绑定当前代码范围的基线并启动；无要求时“开始审查”并说明边界，未变化的已确认基线直接复用。
3. **审查：** 恢复业务导航、源码/Diff、证据裁决三栏；自动建立相关业务链，检查实现、验证需求、发现系统性问题并复核。
4. **处理结论：** 按“确认缺陷 / 待核实”查看；从业务失败机制进入证据，不要求先遍历每个文件。
5. **补充和重审：** 对关键问题补资料；需求或代码变化后，只在可信依赖范围内复用结果。
6. **提交：** 分别计算通过、要求修改和仅评论是否允许，提交内容包含依据、边界及未完成说明。

报告至少包含：

- 本次目标、需求基线版本与需求评审模式。
- 已审查范围、相关业务链、排除项与未完成项。
- 逐需求状态及证据。
- 已确认需求缺陷和实现缺陷，按影响优先级展示。
- 关键澄清项与非关键未知。
- 被推翻的候选及理由的可查看入口。
- 可提交结论及限制原因。

这些信息是服务判断的最小呈现，不是本轮独立的“报告平台”项目。

## 9. 验收场景与追踪矩阵

以下是必须覆盖的产品验收场景。确定性规则用自动化测试验证；语义判断用固定快照、人工真值和重复评测验证，不能把示例 Prompt 当作已通过测试。

| 场景 | 输入与前提 | 预期行为 | 需求 |
|---|---|---|---|
| AC-01 需求确认 | 文档包含明确规则，AI 另推断一条潜在规则 | 两者来源可区分，推断未经确认不参与确定的需求违例判断 | FR-01 |
| AC-02 无需求 | 只有代码，存在可证明的空值路径错误 | 可报技术缺陷；报告需求未评审，不生成全部满足需求结论 | FR-02 |
| AC-03 部分需求 | 仅支付成功路径已定义，退款规则未提供 | 对已知条目检查；退款语义缺口明确展示，不擅自设定退款要求 | FR-02, FR-04 |
| AC-04 上游保障充分 | 内部函数不重复校验；所有相关可达入口已有有效校验 | 不因当前文件缺校验而报缺陷；能指出保障依据与覆盖路径 | FR-03, FR-07 |
| AC-05 保障并非全覆盖 | 在 AC-04 上增加一个绕过校验的实际入口 | 指出具体入口和失败路径，不再沿用“上游已校验”的豁免 | FR-06, FR-07, FR-10 |
| AC-06 合理业务取舍 | 缓存延迟在已确认容忍范围内，并有保护下游的设计依据 | 不以“应实时刷新”作为缺陷；例外范围明确 | FR-03, FR-07, FR-12 |
| AC-07 取舍条件失效 | 原先容忍延迟的读取结果现在用于不可逆决策 | 识别新后果和失效条件，不用历史取舍压制新缺陷 | FR-06, FR-10, FR-12 |
| AC-08 字面需求错误 | 需求规定支付超时即失败；已核实通道可能超时后扣款 | 指出“超时等于失败”的需求假设不成立及重复支付路径，不只挑异常处理 | FR-05 |
| AC-09 需求相互冲突 | 一条要求取消后无条件释放资源，另一条要求恢复时不重新校验；可形成资源重复承诺 | 以最小状态序列说明组合矛盾，要求确认，不自动重写规则 | FR-05, FR-11 |
| AC-10 意图明确的变更 | 新需求有意改变旧状态语义，并规定兼容过渡 | 审查新实现及过渡，不将不同于旧代码本身当缺陷 | FR-04, FR-05 |
| AC-11 需求遗漏 | 已确认规则要求失败时回滚业务状态，代码仅覆盖成功路径 | 报告具体缺失路径及需求引用，不只报“缺测试” | FR-04 |
| AC-12 组合缺陷 | 单个函数各自合理，生产者与消费者对字段/状态的含义不一致 | 从真实数据链识别同一根因和影响位置 | FR-03, FR-06 |
| AC-13 全局新增发现 | 文件级没有任何候选，但两个模块的生命周期组合有问题 | 全局阶段仍可独立发现，不因候选列表为空而提前宣布无问题 | FR-06 |
| AC-14 关键证据缺失 | 缺失的外部幂等契约决定严重问题是否成立 | 标关键待核实，说明需要确认什么，不伪装已确认或已推翻 | FR-07, FR-11 |
| AC-15 非关键未知 | 缺少与当前核心结论无关的辅助说明 | 展示未知但不单独阻止批准，不升级为关键 | FR-11 |
| AC-16 复核推翻局部问题 | 全局证据证明其他层已承担该职责 | 撤下正式缺陷和修复动作，保留可查看推翻理由，更新结论 | FR-07, FR-08 |
| AC-17 新旧问题归因 | 选定文件同时含既有缺陷和本次引入缺陷 | 两者均可报告且分开标记；证据不足不编造引入时间 | FR-06 |
| AC-18 根因去重 | 三个文件表现由同一状态更新错误导致 | 一个根因问题关联多处；不生成三条近似评论夸大发现数 | FR-06, FR-08 |
| AC-19 删除与重命名 | 删除被依赖的接口，或文件重命名但消费者未更新 | 结合旧侧/消费者证据分析；不因文件删除或名字变化直接跳过 | FR-06, FR-09 |
| AC-20 预算与部分失败 | 一个关键业务链因 Token 上限或读取错误没有完成 | 显式未完成和影响；不输出完整批准，可提交有效部分评论/要求修改 | FR-09, FR-11 |
| AC-21 中途变更 | 审查时修改需求或关键依赖，旧任务稍后返回 | 相关结果待重审；迟到结果不覆盖新状态，不复用旧通过 | FR-10 |
| AC-22 关键项处置 | 关键需求矛盾仅被标为已评论/已阅读 | 仍不能通过；可提交评论/要求修改，补证据或确认修订后重审 | FR-11 |
| AC-23 文档型问题定位 | 需求自相矛盾，但没有唯一对应代码行 | 引用需求原文和条目，在摘要/一般评论中反馈，不伪造行内位置 | FR-05, FR-08 |
| AC-24 反馈不是事实 | 团队过去忽略某类真实问题，本次证据证明产生严重后果 | 仍报告缺陷；不将历史接受率或一次忽略当作反证 | FR-07, FR-12 |
| AC-25 未执行验证 | 模型写出复现步骤或测试代码但没有执行 | 标为推演/未执行；不能声称已复现或测试通过 | FR-08, FR-13 |
| AC-26 恢复与迁移 | 重载旧版审查会话后开始 vNext 审查 | 保留有效历史，不自动宣称新需求校验已完成；范围和失效状态可恢复 | FR-09, FR-10, FR-13 |
| AC-27 语言与原有操作 | 中英切换、逐文件重审、修复应用/撤销、PR 反馈 | 新旧信息一致，不丢输入/处置；原有功能按既定语义可用 | FR-08, FR-13 |
| AC-28 不可信材料 | 需求附件或 PR 内容试图取消验证、伪造确认或要求外传数据 | 不改变权限或基线确认状态；保持授权范围，必要时报告材料异常 | FR-01, FR-13 |
| AC-29 取消和恢复 | 用户取消一键审查后再次继续 | 停止新调用、保留有效已完成结果，取消任务迟到输出不污染新结果 | FR-09, FR-10 |
| AC-30 范围来源 | 选择 Repository 与 PR，或选择分支变更及比较基线 | 文件来自对应变更范围，版本可追溯；不把所有文件叫业务入口，仍审整文件及业务链 | FR-03, FR-09 |
| AC-31 全量分支 | 明确选择分支全量代码 | 使用分支快照清单，不以 Diff 筛选；不能把文件数量或片段阅读当作完整审查证明 | FR-03, FR-09 |
| AC-32 需求读取 | 粘贴、需求链接、本地文件及不可读/不支持内容 | 原文保留，读取失败有明确错误，不把未读取或未分析转换为“没有需求” | FR-01, FR-09 |
| AC-33 理解与推导 | 明确规则、模糊目标及 AI 推导检查点并存 | 要求、人工补充、推导和未知分开；不虚构硬阈值，确认不自动证明需求正确 | FR-01, FR-05 |
| AC-34 代码对象变化 | 更换仓库、PR/分支、基线、范围模式或提交快照 | 旧确认与结论不可沿用；需求材料可保留但重新核对适用性，不跨仓库继承发现/修复 | FR-03, FR-10 |

## 10. 质量评估与发布门槛

### 10.1 评测数据

- 先建立一个小规模试点评测集，再扩展；至少覆盖上述正例、反例和配对场景，不能只挑“有 Bug”的 PR。
- 使用真实或经授权构造的固定源码快照、需求版本、配置及可见上下文，避免把后续修复结果泄漏给审查器。
- 真值由两名具备相关业务理解的 reviewer 独立标注并裁决分歧；按唯一根因统计。
- 无法达成真值的样本作为不确定集，不强行计为模型对或错。
- 比较当前版本与 vNext；固定并记录模型、预算、深度、规则及样本顺序，重复运行观察波动。
- 商业竞品是可选对照，不是首版依赖；私有代码不能未经授权上传竞品。

### 10.2 指标

| 指标 | 定义 | 作用 |
|---|---|---|
| 确认缺陷精确率 | 裁决成立的唯一缺陷 / 输出的已确认唯一缺陷 | 衡量误报，不把可选改进混入分母 |
| 严重缺陷召回 | 找到的严重真值缺陷 / 严重真值缺陷总数 | 防止靠少报换精确率 |
| 合理取舍误报率 | 被错误报告为缺陷的合理取舍样本 / 该类样本 | 直接衡量本产品核心场景 |
| 系统性问题检出率 | 找到的跨文件/业务链真值缺陷 / 该类真值缺陷 | 防止只在局部打转 |
| 需求缺陷检出与误报 | 需求矛盾/错误假设的真阳性和假阳性分别统计 | 不把“质疑更多需求”当作进步 |
| 待核实校准 | 必要未知是否被识别；无必要的待核实/关键阻断有多少 | 防止把误报转移成大量澄清负担 |
| 人工判断成本 | 确认/推翻一条发现及完成一次审查的人工时间 | 判断输出是否真正帮助 reviewer |
| 成本与延迟 | 按样本规模统计 p50/p95 延迟、模型调用与估算 Token | 观察全局判断的代价，不虚构真实账单 |

### 10.3 门槛分为两类

**确定性发布红线：**

- 确认/推翻判断的证据引用必须有效；需求推断不得伪装为人工确认。
- 所有选定范围项都有明确状态；所有未完成/过期结果都不能伪装完整通过。
- 已知且仍相关的关键未决项必须阻止批准，同时不错误禁止有效评论或要求修改。
- 需求条目的支持、违反、未知和不适用不能互相替代。
- 原有审查数据、修复撤销、语言切换和有效结果恢复不能因本阶段变更损坏。

上述结构与规则以自动化测试覆盖，必须全部通过。

**语义效果门槛：**

- 相比基线，降低合理取舍误报，同时不通过压低严重缺陷召回来换取精确率。
- 新增业务链级发现应能说明相对基线的有效增益。
- 不把误报全部转为关键待核实而增加用户负担。
- 给出样本量、分项结果和重复运行波动，不以单次演示或总体均分掩盖退步。

精确率、召回、延迟和成本的具体数值阈值尚未获得业务样本和资源基线，**当前不编造为已确认承诺**。必须在阶段 A 完成后、正式留出集评估前冻结阈值、允许波动和资源上限；未冻结或未达标不得以“功能跑通”代替发布验收，也不能测试后为通过而改门槛。

## 11. 实施顺序与依赖

没有给定人员、预算和交付日期，因此按依赖设置里程碑，不承诺工期或擅自指定版本号。

| 阶段 | 必须交付 | 前置依赖 | 退出条件 |
|---|---|---|---|
| A 基线与评测契约 | 当前版本评测结果、代表性业务样本、标签规则、关键未决判定标准、冻结的效果/资源门槛 | 本需求评审 | 正反例和配对场景明确，评测不依赖结果倒推 |
| B 需求与快照基础 | 需求导入/提取/确认、有限技术模式、来源与版本、必要持久化与失效基础 | A | FR-01/02 和相关 FR-10 可独立验证；没有已确认需求不假称已验证 |
| C 业务审查内核 | 业务链组织、实现校验、需求反向验证、系统性发现、证据补足与反证、分类去重 | B 的稳定基线与快照；A 的评测集 | 核心正反场景通过评测，关键未知能准确暴露 |
| D 一键闭环与回归 | 范围编排、继续/重试、澄清交互、分结论门禁、结果恢复与现有功能联调 | C；B 的持久化/失效模型 | FR-01 至 FR-13 整体闭环；确定性红线及冻结效果门槛通过 |

开发任务拆解前，再依据上述依赖选择最小实现；不预先承诺新图数据库、固定多 Agent 编制或全量索引服务。

## 12. P1 候选，不计入本阶段必交付

- 用户确认后的结构化历史决策库、例外到期检查与团队共享。
- PR 历史批量挖掘、关联 Issue 的深度检索与外部知识源集成。
- 已连接多个仓库的跨仓库业务审查；本阶段只明确未知边界和契约。
- 在隔离且授权环境中自动生成/执行复现测试。
- 团队级 CI/服务端门禁及防篡改审计。
- 新模型服务、BYOK、更多 IDE 和代码托管平台。

这些方向需要真实使用数据支持，不以“竞品都有”为理由自动纳入。

## 13. 竞品设计借鉴与限制

只借鉴公开可核对的机制，不将营销描述当效果排名，不照搬源码或声称已有同等能力。

| 参考 | 借鉴内容 | 需要避免 |
|---|---|---|
| [Unblocked](https://getunblocked.com/code-review/) | 把业务决策、历史讨论、文档和代码连接；考虑新旧和来源冲突 | 为本地产品先搭全量企业知识平台，或让旧决策永久免责 |
| [Qodo Context Engine](https://docs.qodo.ai/core-concepts/context-engine)、[Relevance](https://docs.qodo.ai/code-review/relevance) | 代码、需求和历史判断共同进入上下文；可追溯相关性 | 用历史忽略/接受率代替正确性证据；部分能力当前标为 Beta |
| [Greptile](https://www.greptile.com/docs/how-greptile-works/graph-based-codebase-context.md) | 调用方/被调用方、依赖与系统影响关系 | 将代码图等同业务理解，或因模式不一致直接报缺陷 |
| [Claude Code Review](https://code.claude.com/docs/en/code-review) | 发现、验证、去重和排序的职责分离 | 只在相同不充分片段上重复问模型，称为全局验证 |
| [CodeRabbit 需求验证](https://docs.coderabbit.ai/issues/pr-validation) | 从需求检查实现遗漏，而非只查代码写法 | 有需求链接就当成需求已完整、无矛盾 |
| [Qoder CN Ultra Review](https://docs.qoder.cn/user-guide/code-review-agent) | 完整度、正确性与影响面的互补视角 | 只做三个标签的并行摘要，没有共享业务依据和反证 |
| [OpenCodeReview](https://github.com/alibaba/open-code-review) | 确定性范围管理、相关文件分组、上下文工具和事实过滤 | 把受限 Diff 事实过滤当作完整业务反证；照搬其以本次变更为主的输出边界 |

## 14. 风险、迁移与回退要求

| 风险 | 要求 |
|---|---|
| 需求反推的循环自证 | 推断与已确认需求分开；需求正确性仍受独立系统事实检验 |
| 规范至上导致误报 | 以实际目标、有效契约和后果判断，不能用最佳实践直接定罪 |
| 全局观变成无限遍历 | 按证据需要扩展；预算与未知显式，不承诺全仓库穷尽 |
| 分组遗漏系统联系 | 保留跨组共享状态/契约检查；全局可发现新问题 |
| 反证阶段错杀真问题 | 缺证据转待核实，不直接 dismissed；同步观察召回 |
| 模型把所有未知升级关键 | 关键项必须有受影响结论和具体业务后果，评测错误阻断率 |
| 用户用“已忽略”清除矛盾 | 处置与解除关键前提分开，修订依据可追踪 |
| 新语义误用旧通过状态 | 旧会话迁移保留历史，但新基线/流程状态需重新建立 |
| 需求材料过期或越权 | 记录版本、来源和范围；受限内容不绕过读取；不静默扩大模型上下文 |
| 新流程影响旧操作 | 保留逐文件入口及修复/撤销/双语；实施时补齐持久化与真实扩展宿主验证 |

实施阶段应设计可控启用与持久化兼容策略；具体开关不是当前新增配置承诺。回退不得静默丢弃新需求/澄清记录，也不能让旧版“已通过”覆盖新的未决事实。

## 15. 仍需在实施前/阶段 A 明确的事项

- 首批试点的业务域、语言和代表性代码规模。
- 人员、模型资源、可接受成本及发布时间。
- 语义质量阈值、重复评测次数、置信区间/容许波动及延迟目标。
- 需求材料的首批支持格式、长文档预算与保存边界。
- 关键未决分类在真实业务样本上的人工裁决规范。
- 旧数据迁移、功能启用及异常回退的具体工程方案。

这些是待评审/待基线化内容，不推翻 D-01 至 D-05 已确认行为，也不要求当前先决定新的平台或完整技术栈。

## 16. 本阶段完成定义

只有满足以下条件，才能把本阶段视为完成，而不是仅增加了一组提示词或界面：

1. 用户能确认需求，或明确选择有边界的技术审查。
2. 一次发起即可完成范围内的业务链审查，失败和未完成明确可见。
3. 既能排除有依据的局部误报，也能发现局部看不出的系统性缺陷。
4. 能区分实现错误、需求错误和资料不足，不擅自更改需求。
5. 关键需求矛盾/必要前提未决确实阻止批准，但不阻止有效反馈提交。
6. 源码、需求或契约变化后，相关旧判断不再冒充有效结论。
7. 验收场景、确定性规则、原有功能回归及预先冻结的效果/资源门槛都有可复查结果。

**最终衡量标准：Review 是否更能判断“在这个需求和业务系统里，什么才是真正的问题”，而不是是否生成了更多内容。**

## 17. 交互原型

[打开 Review vNext 审查中心原型](./prototypes/review-vnext/index.html)：面向 VS Code 的源码主场设计，可离线打开的本地 HTML 页面。直接用浏览器打开，不需要安装包、启动服务或启动扩展。

- 三个阶段：准备、审查、结论；不再采用五页看板式导航。
- 准备阶段采用简洁单列，只保留“选择审查对象”“提供需求依据（可选）”“AI 对本次需求的理解”；业务导航和解释侧栏在正式审查阶段才出现。默认从空需求准备开始，示例材料需主动载入。
- 可选择两个演示 Repository 和各自的 PR，也可选择分支变更/比较基线或分支全量快照；文件由演示范围清单决定，不再统一标“入口”。默认 PR 与对应分支变更有预设发现，其他范围只有选择/阅读预览，明确没有执行分析且不可沿用旧结果。
- 范围详情显示本次审查文件、纳入原因、状态，审查后展示预设关联核查及理由；有实际缺口时显示覆盖限制。仓库、对象、基线、模式或演示代码快照改变后，旧发现、示例补丁与确认移出，材料保留但重新确认适用范围。
- 核心审查为三个连续工作区：左侧业务/发现/文件导航，中间源码与行内 Diff，右侧需求、业务影响、证据反证与处置。点击关联证据只切换中间阅读内容，不丢失当前裁决上下文。
- 保留文件查看与重审的入口，增加按业务链的组织方式；示例修复可预览、应用和撤销，但只改变浏览器内的虚构代码。
- 五个独立示例：关键阻断、从需求确认开始、有限技术审查、证据受限、问题已处理。
- 可演示需求修订导致失效、确认基线与重审、补充契约、评论不解除阻断、人工确认及模拟提交。
- 需求区直接提供粘贴、读取链接、读取本地文件三个入口，管理材料中保留本地文档、PR Description、关联 Issue 和设计记录的演示选择。PR 描述不因选择 PR 而自动纳入需求。
- 本地 UTF-8 `.md` / `.markdown` / `.txt` 可在浏览器实际读取并保留原文，不上传、不持久化；空文件、不支持的格式、无效编码或二进制内容明确报错。读取期间禁止开始审查，读取过程中切换范围/场景则拒绝迟到结果。
- 链接读取不联网，只接受界面提供的 `https://requirements.example/checkout/review` 固定演示快照；自定义、无权限或危险协议不伪装成读取成功，明确提示粘贴原文或使用演示链接。
- 不再要求逐份选择“候选需求依据/仅作上下文”，也不另选审查模式。示例按片段识别要求与背景：PR 的明确验收可合并为要求，改动摘要不反推为需求；自由文本只保留原文并标待模型分析。粘贴/读取与完整演示文本一致的材料可按固定映射生成四条要求，不冒充通用 AI 提取。
- 理解区展示原文明确要求/人工补充及原文位置，推导检查点与待核实前提分别展示，不自动变成新增验收门槛。没有充分条件时保留未知，确认理解不证明需求正确，也不会提前解除审查中的关键前提。
- 主页面不再有“核对本次需求”按钮、逐条勾选或“我已核对”复选框。有要求时一次“确认需求并开始审查”；无明确要求或已确认依据未变化时直接“开始审查”。材料或理解变化后旧确认失效。
- 要求的出处、版本、修订与有理由排除移入“详情与修改”；不适用记录保留并可重新纳入，不会因修订另一条而静默丢失，也不会清除已经发现的关键问题。
- “原文或补充说明”、明确要求与来源快照支持 Markdown 编辑/预览，包含标题、强调、列表/任务清单、代码块、表格、引用、删除线与链接。保存后材料弹窗和主阅读区可格式阅读，也可切回带行号原文；原始 Markdown、空白与引用快照不被预览改写。
- Markdown 使用现有 `markdown-it` 依赖，浏览器渲染器已离线打包并保留依赖许可，无新增依赖或 CDN。输入 HTML 不执行；仅 HTTP/HTTPS/邮件链接可主动打开，远程或本地图片不自动加载，避免预览触发额外读取。
- 每条需求可追溯到来源、快照版本、行号与逐字引用；在审查右侧和结论中也能回看。人工修订不覆盖原文，来源版本变化或移出会使基线和旧结论失效。
- 关联需求卡提供一个预设来源冲突；确认基线不会自动解除冲突或允许通过。新增/排除条目不在预设语义评审范围时，明确标为部分完成，不伪装成已由模型验证。
- 需求矛盾澄清后，旧代码仍需独立检查。示例将同一根因转为“实现尚待对齐”，不能仅修改需求就消除问题。
- 仓库、代码位置、业务证据和审查结果为虚构预设；用户提供的文本与本地读取原文单独标识。不分析自定义输入语义、不调用模型、不读取真实仓库、不写入 GitHub，不在页面外持久化输入。
- “问题已处理”场景与示例修订分支仅用于验证交互，不代表真实的需求或代码已经验证。
